1. The Problem

A scheduler answers a simple question:

When should a job run?

Examples:

  • Run a report every day at 00:00.
  • Send a reminder 30 minutes before an appointment.
  • Check expired orders every 5 minutes.
  • Process a cleanup task every Sunday.

In a single application, a cron job may be enough:

Cron │ ▼ Application │ ▼ Execute Job

The problem appears when the application has many instances:

Load Balancer / | \ / | \ Server 1 Server 2 Server 3 │ │ │ Cron Cron Cron │ │ │ └────────┼────────┘ ▼ Same job runs 3 times!

In a distributed system, we need coordination and fault tolerance.

2. Why Distributed Systems Make Scheduling Hard

There are several important failure modes.

Duplicate scheduling

Multiple scheduler instances may decide that the same job is due.

Scheduler crash

The active scheduler can fail while jobs still need to be scheduled.

Worker crash

A worker can process a job and crash before acknowledging completion.

Network failure

A request may time out even though the remote service actually processed it.

Key distributed-systems principle: Assume that failures and duplicate deliveries can happen. Design the system so that these cases are safe.

3. High-Level Architecture

A clean design separates scheduling from execution.

┌──────────────────┐ │ Scheduler │ └────────┬─────────┘ │ creates due jobs │ ▼ ┌──────────────────┐ │ Job Database │ └────────┬─────────┘ │ ▼ ┌──────────────────┐ │ Message Queue │ │ Kafka / RabbitMQ │ └────────┬─────────┘ │ ┌─────────────┼─────────────┐ ▼ ▼ ▼ Worker 1 Worker 2 Worker 3 │ │ │ └─────────────┼─────────────┘ ▼ Business Services

Responsibilities

ComponentResponsibility

4. Leader Election & Distributed Locks

The scheduler itself should normally be highly available. That means multiple scheduler instances can exist:

Scheduler 1 ─┐ Scheduler 2 ─┼──► Distributed Lock / Leader Election Scheduler 3 ─┘

Only one instance should actively schedule a particular workload.

Scheduler 1 │ ├── acquires lease │ ▼ LEADER │ ├── scans schedules ├── creates due jobs └── publishes jobs Scheduler 2 → STANDBY Scheduler 3 → STANDBY

If the leader crashes and its lease expires, another scheduler can take over.

Possible technologies

  • Database advisory locks or lease rows
  • Redis-based locks
  • etcd
  • ZooKeeper
  • Kubernetes leader election
Prefer a lease with an expiration time rather than a permanent lock. Otherwise a crashed scheduler could leave the system permanently locked.

5. Job Queue & Workers

After determining that a job is due, the scheduler should hand execution to workers through a queue.

Scheduler │ │ Job: CHECK_EXPIRED_ORDERS ▼ Message Queue │ ├──────────► Worker 1 │ ├──────────► Worker 2 │ └──────────► Worker 3

Examples of queue technologies include Kafka, RabbitMQ, Amazon SQS, and other managed messaging systems.

Example job message

{
  "jobId": "job-123",
  "type": "CHECK_EXPIRED_ORDERS",
  "scheduledAt": "2026-08-19T10:00:00Z",
  "attempt": 1
}

The queue provides buffering and allows workers to scale independently.

6. Job State Machine

Track job lifecycle explicitly.

┌───────────┐ │ SCHEDULED │ └─────┬─────┘ │ ▼ ┌───────────┐ │ QUEUED │ └─────┬─────┘ │ ▼ ┌───────────┐ │ RUNNING │ └─────┬─────┘ / \ / \ ▼ ▼ SUCCESS FAILED │ ▼ RETRY │ ┌──────┴──────┐ │ │ ▼ ▼ SUCCESS DLQ

Useful states include:

  • SCHEDULED Job exists and is waiting for its execution time.
  • QUEUED Job has been published to the queue.
  • RUNNING A worker is processing it.
  • SUCCESS Processing completed successfully.
  • FAILED Processing failed.
  • DLQ Maximum retries were reached.

7. Idempotency & Duplicate Execution

This is one of the most important concepts in distributed job processing.

Consider this sequence:

Queue │ ▼ Worker │ ├── processes job │ └── crashes before ACK │ ▼ Queue redelivers │ ▼ Worker processes again

The system must tolerate this.

Idempotency

An operation is idempotent when repeating the same operation does not create an unintended additional effect.

One approach is to store an idempotency key:

job_id = "job-123"

if already_completed(job_id):
    return

execute_business_operation()

mark_completed(job_id)

A database table might contain:

job_execution
--------------------------------
job_id        status
--------------------------------
job-123       COMPLETED
job-124       COMPLETED
job-125       RUNNING
Important: A distributed scheduler should not depend on exactly-once execution unless the entire underlying system genuinely provides it. Design for safe duplicate delivery instead.

8. Retries & Dead Letter Queue

Temporary failures should usually be retried.

Attempt 1 │ └── FAIL │ ▼ wait 1s │ ▼ Attempt 2 │ └── FAIL │ ▼ wait 2s │ ▼ Attempt 3 │ ├── SUCCESS │ └── FAIL │ ▼ DLQ

Exponential backoff

A common retry pattern is:

delay = baseDelay × 2^(attempt - 1)

Example:

AttemptDelay
11 second
22 seconds
34 seconds
48 seconds

In production, add jitter so that many workers do not retry at exactly the same moment.

Dead Letter Queue

If a job fails repeatedly, move it to a DLQ for inspection or controlled reprocessing.

9. Database Design

A simple relational model could contain two tables.

Schedules

CREATE TABLE schedules (
    id              UUID PRIMARY KEY,
    name            VARCHAR(255) NOT NULL,
    job_type        VARCHAR(100) NOT NULL,
    cron_expression VARCHAR(100),
    next_run_at     TIMESTAMP NOT NULL,
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL
);

Job Executions

CREATE TABLE job_executions (
    id              UUID PRIMARY KEY,
    schedule_id     UUID NOT NULL,
    status          VARCHAR(30) NOT NULL,
    attempt         INTEGER NOT NULL DEFAULT 0,
    scheduled_at    TIMESTAMP NOT NULL,
    started_at      TIMESTAMP,
    completed_at    TIMESTAMP,
    last_error      TEXT,
    created_at      TIMESTAMP NOT NULL
);

Useful indexes should be added for queries such as:

SELECT *
FROM schedules
WHERE enabled = true
  AND next_run_at <= NOW();

11. Failure Scenarios

FailureDesign response
Scheduler crashesAnother scheduler acquires the lease.
Worker crashesQueue redelivery / visibility timeout.
Network timeoutTimeout + retry with backoff.
Duplicate jobIdempotency key / execution record.
Database unavailableRetry carefully and alert.
Permanent business errorMove job to DLQ.
Slow jobWorker lease/heartbeat and timeout policy.
Queue overloadedBackpressure and worker autoscaling.
Avoid infinite retries. A permanently broken job can otherwise consume resources forever.

12. Production Architecture

┌──────────────────────┐ │ API Gateway │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ Scheduler API │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ PostgreSQL │ │ schedules + jobs │ └──────────┬───────────┘ │ ┌──────────▼───────────┐ │ Leader Election / │ │ Distributed Lease │ └──────────┬───────────┘ │ ┌──────────▼───────────┐ │ Scheduler Workers │ │ 1 / 2 / 3 │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ Message Queue │ │ Kafka / RabbitMQ/SQS │ └──────────┬───────────┘ │ ┌────────────────┼────────────────┐ ▼ ▼ ▼ Job Worker 1 Job Worker 2 Job Worker 3 │ │ │ └────────────────┼────────────────┘ ▼ Business Services ┌─────────────────────────────────────────┐ │ Observability │ │ Logs │ Metrics │ Traces │ Alerts │ └─────────────────────────────────────────┘

Key design principle

Keep the scheduler responsible for when and workers responsible for how.

This allows the execution layer to scale independently from the scheduling layer.

13. Design Checklist

  • □ Can multiple scheduler instances run safely?
  • □ Is leader election or distributed locking implemented?
  • □ Does the lock/lease expire if a scheduler crashes?
  • □ Are schedules persisted in durable storage?
  • □ Are jobs distributed through a durable queue?
  • □ Can workers scale horizontally?
  • □ Is duplicate delivery safe?
  • □ Are operations idempotent?
  • □ Are retries limited?
  • □ Is exponential backoff used?
  • □ Is jitter used for large-scale retries?
  • □ Is there a Dead Letter Queue?
  • □ Are job states and execution history persisted?
  • □ Are timeouts and worker leases defined?
  • □ Are logs, metrics, traces, and alerts available?
