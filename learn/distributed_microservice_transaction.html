1. What is the distributed transaction problem?

Imagine an e-commerce workflow:

1. Create Order
2. Reserve Inventory
3. Charge Payment
4. Create Shipment

In a monolith, one database transaction could potentially protect multiple updates. In microservices, each service owns its own database:

                  ┌──────────────┐
                  │ Order        │
                  │ Service      │
                  │ Order DB     │
                  └──────┬───────┘
                         │
                         ↓
                  ┌──────────────┐
                  │ Inventory    │
                  │ Service      │
                  │ Inventory DB │
                  └──────┬───────┘
                         │
                         ↓
                  ┌──────────────┐
                  │ Payment      │
                  │ Service      │
                  │ Payment DB   │
                  └──────────────┘
Example failure: Order succeeds, inventory succeeds, payment fails. Now the system has to decide what to do with the successful previous operations.

2. Local transaction vs distributed transaction

LOCAL

Database Transaction

BEGIN;

INSERT order;
UPDATE customer;
INSERT outbox_event;

COMMIT;

One service controls one database and can use normal ACID transactions.

DISTRIBUTED

Multiple Services

Order DB       Payment DB
   |              |
   +------ ? -----+
       atomic?

Independent databases cannot normally be treated as one local ACID transaction.

Design principle: keep local transactions strongly consistent, then use messaging and business-level coordination across services.

3. Two-Phase Commit (2PC)

2PC uses a coordinator to ask all participants whether they can commit.

                 Coordinator
                  /       \
                 ↓         ↓
             Order DB   Payment DB

PHASE 1: PREPARE
Coordinator → Order DB    "Can you commit?"
Order DB    → Coordinator "YES"

Coordinator → Payment DB  "Can you commit?"
Payment DB  → Coordinator "YES"

PHASE 2: COMMIT
Coordinator → Order DB    "COMMIT"
Coordinator → Payment DB  "COMMIT"

Advantage

Can provide coordinated atomic commit across supported participants.

Problem

More coordination, blocking and operational complexity.

Microservices

Often avoided for long-running business workflows.

Rule of thumb: 2PC is a distributed commit protocol; it is not the same thing as a Saga.

4. Saga Pattern

A Saga breaks a business transaction into local transactions and defines compensation for failures.

Create Order
     ↓
Reserve Inventory
     ↓
Charge Payment
     ↓
Create Shipment

Successful Saga

Order       ✅
Inventory   ✅
Payment     ✅
Shipping    ✅

Result: COMPLETED

Failed Saga

Order       ✅
Inventory   ✅
Payment     ❌

        ↓

Release Inventory
        ↓
Cancel Order
Important: Saga compensation is not a database rollback. It is a new business operation that tries to undo the business effect.

Example compensation table

Forward actionCompensation
Create OrderCancel Order
Reserve InventoryRelease Inventory
Charge PaymentRefund Payment
Create ShipmentCancel Shipment

6. Transactional Outbox

Outbox solves a different problem: reliably publishing an event after a local database transaction.

BEGIN;

INSERT INTO orders (...);

INSERT INTO outbox_events (
  id,
  type,
  payload,
  status
);

COMMIT;

Then an outbox publisher sends the event to Kafka:

Order DB
   |
   +--> orders
   |
   +--> outbox_events
             |
             ↓
      Outbox Publisher
             |
             ↓
           Kafka
Without an outbox, this can happen:

DB commit ✅ → Kafka publish ❌ → event missing
With an outbox, the event remains pending and can be retried.

7. Inbox / Idempotent Consumer

Kafka commonly gives at-least-once processing semantics in practical application designs. A consumer can therefore see the same event more than once.

Kafka
  |
  ↓
Service B
  |
  +--> check eventId
  |
  +--> process business transaction
  |
  +--> record processed event

Example:

eventId = evt-10001

processed_events
----------------
evt-10001
evt-10002

If evt-10001 arrives again, Service B can recognize it as already processed.

Inbox pattern: persist received event IDs, or otherwise make the business operation itself idempotent. Prefer a durable database record for critical correctness rather than relying only on a cache.

8. Where Redis fits

Redis is useful, but it does not automatically create one transaction across Redis + Kafka + databases.

Cache

Fast access to frequently used data.

Rate Limit

Atomic counters and TTLs are useful for request limits.

Temporary State

Useful for short-lived workflow or session state.

Idempotency Helper

Can quickly detect repeated requests, with care for durability requirements.

Atomic Operations

MULTI/EXEC and Lua can make Redis-side operations atomic.

Locking

Possible, but distributed locks have subtle failure modes.

Important: Redis transaction ≠ distributed transaction. For example, Redis success followed by Kafka failure is still a cross-system consistency problem. 
Service A
   |
   +------→ Redis
   |
   +------→ Kafka

These are NOT automatically one atomic transaction.

12. Recommended production checklist

Database

  • Use local ACID transactions.
  • Keep each service's database ownership clear.
  • Use constraints for business invariants where possible.

Kafka

  • Use replication.
  • Configure appropriate acknowledgements.
  • Use producer idempotence where appropriate.
  • Monitor consumer lag.

Messaging

  • Use stable event IDs.
  • Use schema/version compatibility.
  • Design for at-least-once delivery.
  • Use retries and DLQ/DLT.

Business workflow

  • Use Saga for long-running cross-service workflows.
  • Define compensation actions explicitly.
  • Persist workflow state.
  • Build reconciliation for stuck workflows.

Redis

  • Use for cache, rate limiting and temporary state.
  • Do not assume Redis makes Kafka + DB atomic.
  • Do not make critical durable business state depend only on cache state.

Observability

  • Correlation ID.
  • Event ID.
  • Saga ID.
  • Distributed tracing.
  • Metrics and alerts.
