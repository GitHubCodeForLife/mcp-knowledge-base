1. Big Picture

The fundamental problem: Service A and Service B are separate components. Once communication crosses a service or network boundary, you must assume that something can fail between the two. 
Client
  |
  v
+-----------+
| Service A |
+-----------+
      |
      | call
      v
+-----------+
| Service B |
+-----------+
      |
      v
   Database

The important question is not simply:

"How do I call B?"

The better question is:

"What happens if A, B, the network, or the database fails at every possible point in the operation?"

Main Problems

1. Network Failure

Even though both services are internal, the network can fail.

  • Connection timeout
  • DNS failure
  • Packet loss
  • Load balancer failure
  • Service unavailable
Solutions:
Timeout Retry Circuit Breaker Load Balancer

2. Partial Failure

Service A      OK
Service B      DOWN
Database       OK

The whole system is not necessarily down. One component may fail while others continue working.

Solutions:
  • Graceful degradation
  • Fallback behavior
  • Timeouts
  • Circuit breakers
  • Queues for asynchronous work

3. Distributed Transactions

Service A DB
     |
     +---- Order

Service B DB
     |
     +---- Payment

A normal database transaction usually cannot atomically update both databases.

Solutions:
  • Saga Pattern
  • Compensating actions
  • Event-driven architecture
  • Two-phase commit in special cases

4. Duplicate Requests / Messages

A → B
     |
     | timeout
     |
A → B   (retry)

B may process the same request twice.

Solution:

Make operations idempotent. 

Request ID = ORDER-123

First request:
ORDER-123 → process

Retry:
ORDER-123 → already processed → return existing result

3. Case 2: Service A → External Service B over HTTP

This case is more difficult because B belongs to another system or company. 

+-----------+                     +----------------+
| Service A |                     | External B     |
|           |                     |                |
| Your DB   |                     | External DB    |
+-----------+                     +----------------+
      |                                    ^
      |                                    |
      +---------- HTTP --------------------+
Important: You do not control B's database, deployment, retry behavior, API implementation, or availability.

Therefore, A should treat B as an unreliable external dependency.

4. Problem 1: Did B Receive / Process the Request?

This is one of the most important distributed-system problems.

Scenario A: B never receives the request

A --------X--------> B

B: nothing happened

A can usually retry.

Scenario B: B receives but processing fails

A -----------------> B
                     |
                     X
                  failed

Retry may be appropriate depending on the error.

Scenario C: B succeeds but response is lost

A -----------------> B
                     |
                     v
                  SUCCESS
                     |
                     X
                response lost

A sees a timeout and does not know whether B succeeded.

Danger: Blindly retrying may create a duplicate operation.

Solution: Idempotency Key

POST /orders

Idempotency-Key: ORDER-123

B stores the result associated with the key. 

First request:

ORDER-123 → create B-999

Retry:

ORDER-123 → return B-999
             do NOT create another order
Best practice: Always ask an external provider whether their API supports idempotency keys or a unique client-generated reference.

5. Problem 2: Keeping A and B Consistent

Suppose A stores an order and B also stores information about that order. 

A DB:
ORDER-123 = PENDING

B:
ORDER-123 = SUCCESS

The two systems temporarily disagree.

You usually cannot make your database and an external HTTP service behave like one atomic database transaction.

Use a State Machine

             PENDING
                |
                v
           PROCESSING
            /       \
           /         \
          v           v
      SUCCESS       UNKNOWN
                      |
                      v
                RECONCILING
                   /    \
                  v      v
              SUCCESS   FAILED

Why UNKNOWN Matters

If B times out, do not automatically assume that B failed. 

A → B
     |
     | B processed successfully
     |
     X
  timeout

A does NOT know the truth.

Therefore the correct state may be: 

UNKNOWN

Then A can retry safely using an idempotency key, query B, or run reconciliation.

Transactional Outbox

Another problem occurs if A saves its database and then crashes before calling B. 

A DB:
Order = PENDING

Application:
CRASHED

B:
No request

Use an Outbox table. 

+--------------------------------+
| A Database                     |
|                                |
| Orders                         |
|   ORDER-123  PENDING           |
|                                |
| Outbox                         |
|   CALL_B ORDER-123             |
+----------------+---------------+
                 |
                 v
              Worker
                 |
                 v
             HTTP → B

Save the order and outbox event in the same local DB transaction. 

BEGIN

INSERT Order
INSERT OutboxEvent

COMMIT

A background worker then processes the outbox.

6. Problem 3: B Has a Long-Running Task

Suppose B needs 30 minutes to complete an operation.

Do not normally keep an HTTP connection open for 30 minutes waiting for the business operation to finish.

Use an Asynchronous Job

|
| POST /orders
v
B
|
| create job

B processes the job asynchronously. 

B
|
v
Worker
|
| long task
|
v

How Does A Know It Finished?

Option 1: Polling

A → GET /jobs/B-12345
B → PROCESSING

A → GET /jobs/B-12345
B → PROCESSING

A → GET /jobs/B-12345
B → COMPLETED

Option 2: Webhook

B
|
| job completed
|
v
POST /webhooks/job-completed
|
v
A

Option 3: Event / Message

B
|
v
Message Queue
|
v
Service A

Which option is best depends on what B supports.

7. Other Reliability Problems

Timeout

Never wait forever for B. 

Connection timeout
Response timeout
Business/job timeout

Retry

Retry transient failures with exponential backoff and jitter. 

Retry 1 → 1 second
Retry 2 → 5 seconds
Retry 3 → 30 seconds
Retry 4 → 5 minutes

Do not blindly retry every error. 

400 Bad Request → usually do NOT retry

500 / 502 / 503 / timeout
                  → potentially retry

Circuit Breaker

B is failing
     |
     v
Circuit OPEN
     |
     v
Stop sending requests temporarily
     |
     v
Try again later

Rate Limiting

B may only allow a limited number of requests. 

A
|
v
Queue
|
| controlled rate
v
B

This protects both A and B.

Backpressure

If B can process 100 requests/second but A receives 10,000 requests/second, A needs to control the flow. 

10,000 requests/sec
        |
        v
      Queue
        |
        | 100/sec
        v
        B

Dead Letter Queue

Some operations may fail repeatedly. 

Queue
 |
 +-- retry
 |
 +-- retry
 |
 +-- retry
 |
 v
Dead Letter Queue
 |
 v
Manual investigation / recovery

8. Security & External API Problems

Authentication

  • API keys
  • OAuth tokens
  • Client certificates
  • Credential rotation

Authorization

Authentication asks: "Who are you?"

Authorization asks: "What are you allowed to do?"

Data Protection

  • Use HTTPS
  • Do not log secrets
  • Do not log sensitive customer information
  • Encrypt sensitive data where appropriate

9. External API Problems

API Version Changes

B may change its API. 

Old:

{
  "orderId": "123",
  "status": "SUCCESS"
}

New:

{
  "id": "123",
  "state": "COMPLETED"
}

Use an adapter/client layer. 

Service A
   |
   v
ExternalBClient
   |
   v
B API

Keep B-specific details isolated from the rest of your application.

HTTP Success ≠ Business Success

HTTP 200

{
  "status": "FAILED",
  "reason": "INSUFFICIENT_BALANCE"
}

Always distinguish transport-level success from business-level success.

10. Observability

When something fails, you need to understand what happened.

Correlation ID

correlationId = ABC-123

A:
ABC-123 order created

A:
ABC-123 calling B

B:
ABC-123 job created

B:
ABC-123 processing

B:
ABC-123 completed

A:
ABC-123 webhook received

Monitor Business Metrics

  • Pending orders
  • Processing orders
  • Unknown orders
  • Failed orders
  • B success rate
  • B error rate
  • B latency
  • Retry count
  • Webhook delay
  • Stuck jobs

11. Reconciliation

Reconciliation is the safety net for distributed integrations.

Periodically compare what A believes with what B believes. 

A says:

ORDER-123 = PENDING

       vs

B says:

ORDER-123 = SUCCESS

Reconciliation updates A: 

ORDER-123 = SUCCESS
Even with retries, idempotency, webhooks, and queues, reconciliation is valuable because real systems eventually encounter unexpected failures.

13. Internal A → B vs External A → B

Problem A → Internal B A → External B
Network failure Yes Yes, more important
Timeout Yes Yes
Retry Yes Yes
Idempotency Important Extremely important
Distributed transaction Possible problem Cannot normally control it
Consistency Problem Major problem
API changes Can coordinate internally Must handle external changes
Availability Can often control infrastructure Depends on provider
Long-running jobs Can design together Must use provider's job/webhook API
Rate limits Can often control both sides Provider may enforce limits
Reconciliation Useful Very important
Security Internal authentication External authentication + credential management

15. Final Mental Model

The core problem is not HTTP.

The core problem is that A and B can fail independently. 

                 Service A
                     |
                     | HTTP
                     v
                 Service B

Possible failures:

A fails
B fails
Network fails
Request is lost
Response is lost
B succeeds but A doesn't know
A succeeds but B is never called
B takes too long
B processes twice
B changes its API
B is overloaded
B is rate-limited
B sends duplicate webhook
B sends webhook late
Database fails
Application crashes

The general solution:

Make the workflow recoverable.

Use:

Idempotency Retry Timeout Outbox Queue Circuit Breaker State Machine Webhook Polling Reconciliation Observability

The most important idea

Don't assume: 

A → B → SUCCESS

Instead, design for:
