1. The Basic Architecture

The basic communication pattern is:

→
Kafka

→

Important: Do not design this flow assuming every step always succeeds. In a distributed system, every network call, process and broker can fail.

Cluster Problem

No suitable leader or in-sync replica is available.

What should Service A do? 

Service A
   |

Better architecture: Use a Transactional Outbox so Kafka availability does not determine whether the business transaction succeeds.

5. Producer Retry Can Create Duplicates

One of the most subtle distributed-system problems is that Service A may not know whether Kafka actually received the event. 

Service A
   |
   | OrderCreated
   v
Kafka
   |
   | message received ✅
   |
   X
ACK lost
   |
   v
Service A thinks:
"Kafka failed"

Service A retries
   |
   v
Kafka

Kafka may now contain two copies of the same logical event. 

OrderCreated eventId=1001
OrderCreated eventId=1001
Solution: Use producer idempotence where appropriate and make consumers idempotent.

7. Idempotent Consumer

Give every event a unique event ID. 

{
  "eventId": "evt-10001",
  "eventType": "OrderCreated",
  "orderId": "order-123",
  "timestamp": "2026-08-21T10:00:00Z"
}

Service B can maintain a table of processed event IDs: 

processed_events

event_id
----------------
evt-10001
evt-10002
evt-10003
1
Receive event

eventId = evt-10001

2
Check processed_events

Has evt-10001 already been processed?

3
If already processed IGNORE

Do not perform the business operation again.

4
If not processed PROCESS

Perform the business transaction and record the event ID.

8. Transactional Outbox Pattern

The Outbox Pattern solves the problem where Service A successfully updates its database but fails to publish the corresponding event.

Service A
Business operation
→
Database
Orders + Outbox
→
Outbox Publisher
Retries
→
Kafka
Event Broker

Database transaction

BEGIN;

INSERT INTO orders (
    id,
    customer_id,
    amount
)
VALUES (
    1001,
    50,
    200
);

INSERT INTO outbox_events (
    id,
    event_type,
    payload,
    status
)
VALUES (
    999,
    'OrderCreated',
    '{...}',
    'PENDING'
);

COMMIT;

If Kafka is down, the event remains in the outbox. 

outbox_events

id     event_type      status
--------------------------------
999    OrderCreated    PENDING
1000   OrderCreated    PENDING
1001   OrderPaid       PENDING

When Kafka becomes available again, the publisher retries the pending events.

Broker 3   Replica
Kafka can elect another eligible replica as the partition leader.

Important configuration concepts

Replication Factor

Determines how many copies of a partition are maintained.

acks=all

Producer waits for the required in-sync replicas to acknowledge the record.

min.insync.replicas

Controls the minimum number of in-sync replicas required for writes when using appropriate producer acknowledgements.

Important: Replication does not protect an event that Service A never successfully publishes. Kafka durability and application-level delivery are different problems.

Some messages fail temporarily. Others are permanently invalid. You should handle these differently.

Dead Letter Topic
TEMPORARY FAILURE

Retry

  • Database temporarily unavailable
  • Network timeout
  • External API temporarily unavailable
  • Temporary Kafka problem
PERMANENT FAILURE

DLQ / DLT

  • Invalid message schema
  • Invalid business data
  • Unsupported event version
  • Repeated processing failure

12. Message Ordering

Suppose Service A produces: 

OrderCreated
OrderPaid
OrderShipped

If these events belong to the same order, you often want them processed in order.

With Kafka, ordering is guaranteed within a partition. A common design is to use the business identifier as the key. 

key = orderId

order-1001
    |
    +--> Partition 3
          |
          +--> OrderCreated
          +--> OrderPaid
          +--> OrderShipped
Do not assume Kafka provides global ordering across all partitions.

13. Event Schema Changes

Service A and Service B may be deployed independently. Therefore, event compatibility matters. 

Version 1

{
  "orderId": 123,
  "amount": 100
}


Version 2

{
  "orderId": 123,
  "amount": 100,
  "currency": "USD"
}

Backward Compatibility

New consumers should still understand older events when required.

Schema Version

Explicitly version important event contracts.

Schema Registry

Kafka environments commonly use schema management tools to enforce compatibility rules.

Recommended reliability mechanisms

✓ Transactional Outbox

Prevents losing an event between a database transaction and Kafka publishing.

✓ Kafka Replication

Protects partition data against individual broker failures.

✓ Producer Idempotence

Helps prevent duplicates caused by producer retries.

✓ Consumer Idempotency

Allows safe processing when the same event is delivered more than once.

✓ Retry Policy

Handles temporary failures.

✓ DLQ / DLT

Separates permanently failing messages from normal traffic.

✓ Consumer Lag Monitoring

Detects consumers that cannot keep up with producers.

✓ Schema Compatibility

Prevents independent service deployments from breaking event contracts.

16. The Mental Model

The most important thing is to stop thinking of the system as simply: 

Service A → Kafka → Service B

Instead, think about every possible failure:

Core principle: In a distributed system, assume that every component can fail, every network call can timeout, messages can be duplicated, consumers can crash, and brokers can become unavailable. Design the system so that recovery is safe.

Key concepts to remember

Outbox

Don't lose events

Store the business transaction and event reliably before publishing.

Idempotency

Handle duplicates

The same event can be processed more than once safely.

Replication

Survive broker failure

Keep replicated copies of Kafka partitions.

Retry

Recover from temporary failure

Retry operations that can succeed later.

DLQ / DLT

Isolate bad messages

Prevent poison messages from blocking normal processing.

Lag

Monitor consumers

Detect when consumers cannot keep up with producers.
